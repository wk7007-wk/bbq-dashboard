# Hynix User Principles Raw

하이닉스 사이트 관련 사용자 원문/의도 원칙의 단일 기록이다. 음성 오타가 있어도 가능한 원문을 보존하고, 필요한 경우 원문 바로 아래 `해석:` 한 줄만 둔다.

## 1) 화면/해상도/필요항목

- "이후 프롬프트부터 차곡 정리. 사이트는 컴퓨터 모니터 폰화면 두개축. 모니터 일반사이즈에 720p정도. 한화면에 중요정보를 최대한 보여주는게 좋아. 필요항목인지 불필요인지 정립이 필요해"
- "제목위주보단 우선은 근무표"
- "제목은 칸구분을 위해 필요하지만 근무표 대비 제목 할당면적이 넓고 굳이 의미나 정보전달역할부재"
- "근무표가 메인에 전부이면서 보조적으로ㅈ가공분석 데이터 별도 표기. 해상도의 한계인데 비율이 불필요가 공간비율의 큰차지가문제"
- "한정 공간으로 탭으로 빠르게 다른형태 진입 상황에 불필요가 우선될필요없음"
- "ui ux는 디자인과 해상도 고려 퀄리티와 사이즈의 밸런스. 한곳도 극단적 방향은 지양"

## 2) 수정 방식/팝업

- "한정 공간을 최적화 방법중.근무수정은 필요하기 때문에 수정기능은 존재.다만 탭과 스크롤은 빠르게 수정이나 반복작업에 불편.대안은 팝업이며 그렇게 구현되어잇을거고 의도에 갱신"

## 3) 사이트 범위/탭/DB

- "사이트는 근무만 작업이 아니라.운영에 필요한 사용자 통합 입출력사이트.출력이 메인.운영메뉴얼도 하나의 탭으로 전환"
- "탭은 지속 추기 예정"
- "db와의 체계적 연계성.사이트는 원천db의 입출력 하나의 창구일뿐.원천db를 다른 채널에서도 최신상태로 입출력 가능한 형태로 지속형태"

## 4) 근무표 내부 탭/출력 방식

- "메인 탭이 있고 근무표 안 해도 내부 탭이 있어. 보여주는 출력 방식에 따라 타임스태프와 기존에 이번 주라고 돼 있던 내용을 같이 합산하는 게 좋을 것 같아. 하루 단위 타임스탬프로 어느 구간에 누가 출근하는지도 한눈에 볼 수 있고 이번 주 라는건 없고 그냥 근무표라고. 메인 근무편의 근무표 표준으로 보는 방식 하나와 최근에 아니지. 날짜별 탭에 타임스탬프와 날짜별 주간 얘 떠야 되고 이번 주와 똑같은 형태지. 추가로 그다음주를 볼려고 하면 화면이 늘어나는 형태 그리고 근무표 내부탭에 직원별로 탭도 두고 직원별 탭은 지금 타임스탬프까지는 필요 없어. 다만 구간 자체의 색상을 동쪽으로 넣어서 어 오전 타임 오후 타임 중간 타임 등 다른 타임이라는 구별의 색감으로 확인할 수 있어야 돼."

해석: `타임스태프`는 `타임스탬프`, `동쪽으로`는 음성 오타로 보고 `구간별 색상 구분`으로 해석.

정리 기준: 내부 탭은 `근무표`, `날짜별`, `직원별`, `기록`. `시간순`은 삭제. `이번주`라는 별도 탭명은 쓰지 않고 `근무표` 기본 보기 역할에 흡수.

## 5) 미래/과거 기록

- "항상 근무편은 미래를 보는 거기 때문에 오늘까지는 보여주되 오늘 이전의 꺼는 보여줄 필요는 없어. 그리고 기록이라는 근무표의 기록이라는 탭도 필요해. 기록은 미래가 아니라 과거야. 과거에 몇 시부터 몇 시까지 근무를 했는지에 대한 부분 그거는 이후에 시급이나 총시간음"
- "인건비와 나중에 연계할 가능성이 있기 때문에 어 보고서는 분상용으로 확장할 수 있게"

해석: `분상용`은 `분석용` 의미.

## 6) 운영매뉴얼

- "운영 매뉴얼은 또한 입출력을 원천지. 위에서 가져오는 형태가 되고 카카오스토어봇에서도 입출력 기능을 같이 맞출거야. 원전 DB가 계속 쌓아가는 형태가 돼야 되고 지속적으로 새로운 입력이 들어올 때 전체 운영 매뉴얼이 제 적립이 돼야 돼. 그리고 사이트에서는 출력본이 처음은 직원이 가게 운영의 시스템을 이해할 수 있는 스트리얼 같은 어 배울 수 있는 규칙을 인지하고 배울 수 있는 문구나 어 방식을 선택해줘. 다만 너무 어렵지 않고 중요한 결정적인 문구들의 포인트로 요약도 필요해 자세한 설명과 요약이 굉장히 잘 분배가 돼야 돼. 꼭 카드형을 고집할 필요는 없어"

해석: `원전 DB`는 `원천 DB`, `스트리얼`은 `튜토리얼`, `제 적립`은 `재정립` 의미.

## 7) 단일 원문/상의 후 구현

- "프로젝트 원칙 토탈원문 기록에두고 분산하지말것. 그리고 하니씩 다른 구간을 분석해서 구현하고 필요한항목인지 아니지 나와 상의후 구현"

해석: 하이닉스 프로젝트 원칙 원문은 단일 raw 문서에 보존. 이후 UI 각 구간은 먼저 분석하고 필요/불필요를 사용자와 상의한 뒤 구현.

## 13) 2026-07-07 NotebookLM식 입력 정리/출력 다양화 원칙 보정

- "NotebookLM 도입 의도는 입력을 요약/정리해서 DB화하고 출력 다양화하는 것. 원칙 갱신. 근무표는 이 방식 도입이 필요한가? 사이트 기능추가 예정인데 사이트 자체 원칙으로 가는 건?"

해석: NotebookLM식 흐름은 사이트 전체 기능 추가 원칙으로 채택한다. 카톡, 사이트, 운영메모, 규칙, 변경요청 입력은 원문과 출처를 보존한 뒤 요약/정리/분류해 내부 DB화하고, 직원용/관리자용/검색형/카톡형/사이트형 출력으로 다양화한다. 단, 근무표 자체는 정형 업무 데이터이므로 `/workschedule_v2` 같은 canonical schedule DB를 직접 원천으로 삼고, NotebookLM식 요약 DB는 자연어 입력을 정형 근무 command로 바꾸거나 변경요청/감사로그/운영메모/과거 기록 리포트/인건비 분석을 설명할 때만 보조로 쓴다. MCP는 이 흐름의 표준 도구 호출/연결층이며, read-only 먼저 열고 write/delete는 인증/감사/명시 승인/권한별 분리 뒤에만 연다.
