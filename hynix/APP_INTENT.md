## 목적
- 하이닉스 사이트/AttendanceBoard는 근무표 단일 화면이 아니라 운영자가 원천 DB를 기준으로 확인, 입력, 출력하는 통합 운영 사이트다.
- 사이트의 기본 우선순위는 출력/조회/확인 흐름이다. 입력/수정은 필요하지만 핵심 출력 흐름과 화면 면적을 밀어내면 안 된다.
- 근무표는 현재 핵심 탭이자 핵심 출력이지만, 사이트 전체 목적을 근무표 하나로 좁히지 않는다.
- 원천 DB가 SOT이며, 사이트는 SOT가 아니라 사용자용 입출력 창구다. 근무 관련 canonical은 기존 원칙대로 `/workschedule_v2`다.
- 운영메뉴얼도 정적 문서가 아니라 원천 DB를 기준으로 직원 교육/운영 규칙 이해를 위해 재구성되는 출력이어야 한다.
- 2026-07-06 최신 확정 요구로 `날짜별` 게이지, 근무칸 overlay 수정 팝업, `사진 확인` UI 비노출은 구현/검증/배포 대상이다. 단, 이 세 범위를 넘어 임의 UI 재해석이나 대규모 재배치는 하지 않는다.
- 근무표/계획 영역은 오늘 포함 미래를 보는 축이고, 기록/실적 영역은 과거 실제 근무를 보는 축이다. 두 시간축을 한 탭 의미로 섞지 않는다.

## DB 연계 원칙
- 사이트에서 입력/수정한 내용은 원천 DB에 즉시, 일관되게 반영되어야 한다.
- 사이트 출력은 사이트 전용 로컬 상태가 아니라 원천 DB 최신 상태에서 계산되어야 한다.
- 카카오, 봇, CLI, 다른 운영 채널도 같은 원천 DB를 기준으로 최신 상태를 읽고 쓸 수 있어야 한다.
- 사이트 전용 로컬 상태, 캐시, 별도 경로, 출력 산출물이 원천처럼 굳어지면 안 된다.
- UI 탭, 운영메뉴얼, 보조 분석은 각자 원천 DB와 어떤 입출력 관계를 갖는지 명확해야 한다.
- 운영메뉴얼 원천은 `/packhelper/ops_manual` 계열 지속형 DB로 본다. 사이트, 카카오/StoreBotTermux, CLI/관리 채널은 같은 원천을 읽고 쓰는 소비자/입력자다.
- 새 규칙, 현장 피드백, 카카오 기록, 운영자 입력은 흩어진 문서가 아니라 운영메뉴얼 원천 DB에 누적되어야 한다.
- 최신 운영메뉴얼 출력은 누적된 원천 DB를 기준으로 다시 구성되어야 하며, 필요하면 분류, 순서, 요약, 상세 구조 전체를 재정립한다.
- 요약, 상세, 중요 포인트는 같은 원천에서 파생되는 출력 형태다. 사이트 전용 문서나 카카오 전용 지식이 원천처럼 굳어지면 안 된다.
- NotebookLM식 도입 의도는 단순 출력 UX가 아니라 카톡, 사이트, 운영메모, 규칙, 변경요청 같은 여러 입력을 원문과 출처와 함께 보존하고 요약, 정리, 분류해 내부 DB화한 뒤 직원용, 관리자용, 검색형, 카톡형, 사이트형 출력으로 다양화하는 것이다.
- 사이트 기능 추가는 `입력 수집 -> 원문 보존 -> 구조화/요약 DB화 -> 출처 기반 다양한 출력` 흐름을 우선 검토한다.
- NotebookLM 자체는 원천 DB나 실행 엔진으로 삼지 않는다. 출처 기반 정리 방식과 출력 다양화 패턴만 참고한다.
- 근무표 자체는 정형 업무 데이터이므로 NotebookLM식 요약 DB를 원천으로 삼지 않는다. 근무표 출력/수정은 `/workschedule_v2` 같은 canonical schedule DB를 직접 기준으로 한다.
- 근무표에 적용되는 범위는 자연어 카톡/사이트 입력을 정형 schedule command로 변환할 때, 변경요청/감사로그/운영메모를 요약해 설명할 때, 과거 기록 리포트/인건비 분석용 해설을 만들 때로 제한한다.
- 모든 탭/출력은 canonical DB와 가공 DB/캐시/요약층을 분리 표시하고, 출력 다양화는 같은 원천에서 파생되어야 한다.
- 의미 요약·다축 분류·태그·관계·taxonomy 재정리는 `rules/ai_knowledge_organization.txt`의 공통 AI 계약을 따른다. 고정 keyword, 첫 문장 추출, 임의 고정 confidence는 의미 분석 결과로 취급하지 않으며, Hynix 원문·taxonomy·승인권은 SolNote와 공유하지 않는다.
- AI는 기본적으로 제안을 만들고, 운영자/사용자가 명시적으로 저장·정리·반영을 요청했을 때만 대상 revision·허용 action·최대 건수·만료시각으로 제한된 1회성 scope를 통해 메뉴얼 draft/entry를 쓸 수 있다. standing credential, raw 수정, hard delete, 카카오 발송, 근무표 변경은 이 scope에 포함하지 않는다.
- Hynix 보안 우선순위는 실수로 원문·직원/고객 식별정보가 외부 AI, 공개 site projection, 일반 로그에 노출되지 않게 하는 것이다. 외부 AI에는 요청 대상의 최소 evidence packet만 보내고 전송 범위를 audit하며 공개 read-model은 field allowlist로 생성한다.
- 표준 MCP는 사이트, 카카오/StoreBotTermux, worker가 같은 호출 규격을 공유하는 연결층이다. 자체 MCP 규격을 만들지 않고 공식 MCP `tools`, `resources`, `prompts` 개념 위에 내부 원천 DB adapter/server를 둔다.
- MCP 공개는 read-only 조회부터 두되, 입력/수정/삭제가 실사용 요구로 확정된 표면은 인증, 감사로그, 명시 승인, 권한별 도구 분리, soft-delete/delete-request guard를 붙여 연다. hard delete와 no-auth mass send는 열지 않는다.
- 현재 구현 포인터: `AttendanceBoard/docs/hynix/knowledge_adapter_contract.json`은 Hynix site가 읽는 write-enabled async contract이며, 운영메뉴얼 영역의 compact panel이 인증 사용자에게 원문 저장 즉시 반영, `/packhelper/ops_knowledge/queue` 정리 상태 표시, 구조화 요약 저장, 출력 variant 저장, 삭제요청, 숨김, 복구를 제공한다. 입력은 DB 반영이고 정리는 후처리다. 실제 구조화 함수와 CLI는 root `scripts/operation_knowledge_adapter.py`에 있고, StoreBot worker는 같은 계약을 `operation_knowledge.ingest/process_queue/process_job/upsert_summary/render_output/request_delete/delete/restore/send_reply` action으로 사용한다. Kakao 출력은 explicit action, room guard, no-send default, audit 조건으로만 열며 검증 중 실제 발송하지 않는다.
- `기록` 탭은 과거 실제 근무 기록을 원천 DB에서 읽고 써야 하며, 사이트 전용 로컬 기록이 원천이 되면 안 된다.
- 기록 데이터는 시작/종료 시간, 총 근무시간, 향후 시급/인건비 계산에 필요한 기준을 보존한다.

- 폰 화면: 모니터와 별도 기준으로 보며, 글씨 잘림과 가로 넘침을 먼저 막는다.
- 두 화면 모두 카드, 긴 설명, 장식 요소를 늘리는 방식보다 실제 운영 정보 밀도를 우선한다.

## UI/UX 균형 원칙
- UI/UX는 디자인 완성도와 해상도 제약을 함께 보며, 정보밀도, 가독성, 터치 편의, 시각적 품질을 균형 있게 판단한다.
- 퀄리티와 사이즈 중 어느 한쪽만 극단적으로 밀지 않는다.
- 720p급 모니터에서는 한 화면 정보량을 늘리되, 글씨가 작아지거나 빽빽하고 조잡한 화면이 되면 실패로 본다.
- 폰 화면에서는 스크롤을 줄이되, 터치 대상, 글자 크기, 팝업 조작성이 희생되면 실패로 본다.
- 제목, 카드, 여백, 장식은 과하면 근무표를 밀어내므로 줄이되, 구분과 사용성에 필요한 최소 품질은 유지한다.
- 금지 예시: 정보량만 늘려 글씨가 작고 빽빽한 화면.
- 금지 예시: 보기 좋게만 만들어 핵심 근무표가 밀려나는 화면.
- 금지 예시: 탭이나 팝업을 과도하게 줄여 조작 의미가 불명확한 화면.
- 금지 예시: 큰 제목이나 카드가 화면 비율을 과하게 차지하는 화면.
- 구현 검증은 모니터와 폰 양쪽에서 정보 노출량과 가독성을 함께 본다.

## 면적 배분 기준
- 화면의 1순위 정보는 가장 중요한 출력/조회/확인 결과이며, 현재 핵심 출력은 근무표다.
- 현재 메인 화면의 거의 전부는 근무표 행/열 노출에 쓰되, 이는 사이트 전체 목적을 근무표 하나로 고정한다는 뜻이 아니다.
- 화면 공간은 한정되어 있으므로 기본 화면은 근무표 내부 `근무표` 보기 중심으로 구성한다. 기존 `이번주` 역할은 여기에 흡수하고, `이번주`를 별도 탭명으로 쓰지 않는다.
- 상위 탭과 근무표 내부 탭을 구분한다. 상위 탭은 통합 운영 사이트의 큰 영역이고, 근무표 내부 탭은 근무표 출력 방식을 바꾸는 장치다.
- 탭은 보조/대체 형태로 빠르게 진입하는 장치이지, 모든 항목을 같은 우선순위로 노출하는 장치가 아니다.
- 상위 탭은 앞으로 계속 추가될 수 있으므로 `출력`, `입력/수정`, `운영메뉴얼`, `보조 분석`처럼 역할이 명확해야 한다.
- 운영메뉴얼은 별도 탭으로 접근하며, 제목만 있는 문서가 아니라 실제 운영자가 볼 내용 중심이어야 한다.
- 운영메뉴얼은 보조 도구 접힘 안에만 숨기지 않고 상단 주요 화면 전환에서 바로 열 수 있어야 한다.
- 운영메뉴얼 탭의 첫 출력 형태는 처음 보는 직원도 가게 운영 시스템을 배울 수 있는 튜토리얼/학습형 규칙 안내다.
- 운영메뉴얼은 핵심 요약, 결정적 포인트, 상세 설명을 함께 제공하되, 어렵거나 긴 텍스트만 나열하지 않는다.
- 운영메뉴얼 화면 형식은 내용에 맞게 선택한다. 카드형 UI는 선택지일 뿐 필수 형식이 아니다.
- 기본 탭/첫 화면에는 현재 상황에서 가장 중요한 출력만 둔다.
- 탭이 늘어나도 낮은 우선순위 탭이 상단, 첫 화면, 핵심 출력 면적을 잡아먹으면 실패로 본다.
- 제목, 헤더, 섹션명은 칸 구분용으로 필요하되 면적은 최소화한다.
- 제목이 설명, 브랜딩, 장식 역할로 화면 높이를 잡아먹으면 정보 전달 가치가 낮은 불필요 항목으로 본다.
- 가공/분석 데이터는 보조 정보로 별도 표기하되, 근무표를 밀어내지 않는 축약, 접힘, 작은 보조 영역으로 둔다.
- 해상도 한계에서는 항목이 존재하는 것 자체보다 불필요하거나 보조적인 항목이 화면 공간 비율을 크게 차지하는 것이 문제다.
- 상황에 불필요하거나 낮은 정보가 기본 화면, 탭 첫 순서, 상단 영역을 차지하면 실패로 본다.
- 보조 분석, 다른 보기, 추가 도구는 필요할 때 빠르게 들어갈 수 있되 근무표 노출 공간을 밀어내지 않게 한다.
- 필요/불필요 판단은 `정보 가치 대비 차지하는 화면 비율`로 본다.
- 720p급 모니터와 폰 화면 모두 제목/보조 정보보다 근무표 행/열을 더 많이 보여주는 것을 우선한다.

## 항목 판단 원칙
- 필요한 항목: 실제 운영 확인, 입력/수정, 출력에 직접 쓰이는 정보.
- 불필요한 항목: 운영 확인/수정/출력에 직접 도움 되지 않거나 첫 화면 정보 밀도를 떨어뜨리는 설명, 중복 버튼, 보조 카드.
- 항목 삭제/유지는 먼저 문서에 기록하고, 사용자 확인 또는 최소 자체 검증 후 구현한다.

## 근무수정 UX 원칙
- 근무표가 메인인 화면에서 한정 공간을 최적화하더라도 근무수정 기능 자체는 없애지 않는다.
- 수정 진입은 별도 탭, 긴 스크롤, 모드 이동이 아니라 근무칸 터치 후 화면 중앙 또는 상단 overlay/modal 팝업을 기본으로 본다.
- 현재처럼 근무표 안에서 펼쳐지는 inline 수정은 반복 수정 뒤 복귀 시 스크롤 부담이 크므로 기본 UX로 쓰지 않는다.
- 저장 또는 닫기 뒤 근무표로 바로 돌아와야 하며, 저장 후 스크롤 위치가 불필요하게 이동하면 안 된다.
- 팝업은 빠른 수정과 반복 수정에 유리해야 하며, 휴무 지정과 시간 변경 같은 핵심 수정은 2-3회 터치 안에 처리되는 것을 목표로 한다.
- 탭은 보기 전환이나 보조 진입 장치이지 반복 수정 작업의 주 진입점이 아니다.
- 구현 확인 시 실제 코드가 이미 팝업 방식이면 그 의도를 유지/강화하고, 탭/스크롤 수정 UX로 퇴행시키지 않는다.

## 탭/보기 기준
- `근무표`: 근무표 내부의 기본/표준 보기다. 메인 근무 편의를 위한 기존 `이번주` 역할을 흡수하되, 탭명은 `근무표`로 본다.
- `근무표` 기본 보기는 오늘 포함 미래 근무 계획만 보여준다. 오늘 이전 계획은 기본 근무표에서 숨긴다.
- `날짜별`: 근무표 내부의 날짜별 보기다. 하루 단위 타임스탬프/게이지로 어느 구간에 누가 출근하는지 한눈에 보여준다.
- `날짜별` 타임스탬프는 실제 API 없이 24시간 고정 그라데이션을 쓰고, 각 근무 막대는 해당 시작/종료 시간 위치의 색상 흐름을 적용한다.
- 프론트 UI에는 명암 설명어를 라벨로 노출하지 않는다. 필요한 텍스트는 `00`, `06`, `12`, `17`, `24` 같은 시간 눈금과 기존 근무 시간 텍스트 정도로 제한한다.
- `00/06/12/17/24` 눈금 숫자는 폰 화면에서도 읽혀야 한다. 그라데이션 위에서 뭉개지지 않도록 굵은 숫자, 밝은 반투명 라벨 배경, 테두리/halo로 배경과 분리한다.
- `날짜별`의 기본 범위는 이번 주다. 다음 주나 추가 주간은 새 탭을 계속 늘리지 말고 화면 아래 확장, 더보기, 접힘 해제처럼 탭 과밀을 피하는 방식으로 추가한다.
- `직원별`: 근무표 내부의 직원별 보기다. 이 보기에는 타임스탬프 게이지까지는 필요 없고, 오전/중간/오후 등 근무 시간 구간 자체를 색상으로 구분한다.
- `기록`: 과거 실제 근무 실적 탭이다. 몇 시부터 몇 시까지 실제 근무했는지와 총 근무시간을 보며, 향후 시급/총시간/인건비 계산과 보고서 분석의 기준 데이터가 된다.
- `기록` 추가는 과거 실적 탭 추가이지 `시간순` 정렬 탭 부활이 아니다.
- `시간순`: 삭제 요구를 유지한다. 타임스탬프는 `날짜별` 안의 시각화 방식이지 `시간순` 탭 부활 근거가 아니다.
- 음성 인식으로 애매한 표현은 새 기능명으로 확정하지 않고, 우선 `구간별 색상 구분`처럼 보수적으로 해석한다.
- `첫근무`, `근무기준일`, `빠른접근`: 메인 첫 화면에서 삭제 후보 또는 삭제 요구로 기록한다. 구현 전 최종 표현을 확인한다.
- `사진 확인`: 현재 범위에서는 메뉴, 보조 도구, 탭, 문구 등 사용자 UI 노출에서 제거한다. 관련 DB나 이미지 처리 경로는 다른 기능에서 필요할 수 있으므로 이번 작업에서 파괴적으로 삭제하지 않는다.
- 잘못 전달된 요구였던 "`이번주`, `직원별`, `시간순` 삭제"를 기준으로 삼지 않는다.
- 최근 잘못된 구현/배포로 보고된 `466c9f5 Polish Hynix schedule UI`는 새 요구 기준의 baseline이 아니다.

## 근무표 표시 규칙
- 오늘 이전 날짜는 표시하지 않는다.
- 이 규칙은 기본 `근무표` 계획 보기 기준이다. 과거 실제 근무는 `기록` 탭에서 본다.
- 주 시작은 월요일이다.
- 빈값은 대체 문구로 채우지 말고 비워둔다.
- 근무 없는 사람은 기본 숨김 또는 하단 정렬로 처리한다.
- `근무표`와 `날짜별` 정보가 720p급 모니터와 폰 화면에서 서로 근무표 공간을 밀어내지 않게 균형 있게 배치한다.
- 보고서/분석은 `기록` 데이터를 기반으로 나중에 확장 가능한 보조 출력이다. 기본 근무표 공간을 밀어내면 안 된다.
- 모바일에서는 버튼/셀/라벨의 글씨가 잘리지 않게 한다.

## 구현 전 상의 절차
- 구간 식별: 수정하려는 UI/기능 구간을 먼저 나눈다.
- 현재 UI 캡처/분석: 720p급 모니터와 폰 화면 기준으로 현재 노출량, 가독성, 조작성을 본다.
- 필요/불필요 판정안 작성: 해당 구간의 항목별 정보 가치와 화면 점유 비율을 정리한다.
- 사용자 확인: 필요한 항목인지, 불필요한 항목인지 상의하고 확정한다.
- 단일 구현 lane 수정: 확정된 구간만 한 작업 lane에서 수정한다.
- 브라우저 검증: 720p급 모니터와 폰 화면에서 직접 렌더링을 확인한다.
- 배포: 검증 뒤 별도 승인된 배포 작업으로 진행한다.

## 구현 전 체크
- 프롬프트별 사용자 원문은 `USER_PRINCIPLES_RAW.md`에 누적하고, 이 문서는 정리본만 갱신한다.
- 통합 운영 사이트 범위, 출력 우선순위, 원천 DB SOT, 사이트의 입출력 창구 역할이 유지되는지 확인한다.
- 새 탭은 역할과 원천 DB 입출력 관계를 먼저 정하고, 기본/첫 화면의 핵심 출력을 밀어내지 않는지 확인한다.
- `기록` 탭은 과거 실제 근무 기록 전용인지, 원천 DB 연결인지, 시작/종료/총시간 기준을 보존하는지 확인한다.
- 운영메뉴얼 탭은 실제 운영자가 볼 내용 중심인지 확인한다.
- 운영메뉴얼 출력이 `/packhelper/ops_manual` 계열 원천 DB에서 파생되는지, 요약/상세/중요 포인트가 같은 원천에서 나오는지 확인한다.
- NotebookLM식 원칙을 사이트 전체 기능 추가 기준으로 검토하되, 근무표 자체에는 전면 도입하지 않고 기능별 보조 적용 범위를 분리했는지 확인한다.
- 입력 원문과 출처 보존, 구조화/요약 DB화, 직원용/관리자용/검색형/카톡형/사이트형 출력 파생 관계가 같은 원천을 기준으로 유지되는지 확인한다.
- 운영메뉴얼의 출처 기반 요약 UX는 NotebookLM 방식을 참고하되, NotebookLM 자체를 원천 DB나 실행 엔진으로 쓰지 않는지 확인한다.
- 근무표 출력/수정 원천이 `/workschedule_v2` canonical schedule DB로 유지되고, 요약 DB/캐시/출력 산출물이 원천처럼 쓰이지 않는지 확인한다.
- 표준 MCP 연계가 공식 `tools`, `resources`, `prompts` 개념을 따르고 내부 원천 DB adapter/server를 거치는지 확인한다.
- MCP write/delete 도구는 인증, 감사로그, 명시 승인, 권한별 분리, soft-delete/delete-request guard를 갖춘 표면에서만 열렸는지 확인한다.
- 운영메뉴얼 입력이 사이트/카카오/StoreBotTermux/CLI 중 어느 채널에서 들어와도 같은 원천 DB에 누적되는지 확인한다.
- 구현 전 기존 `이번주` 역할이 내부 `근무표` 보기로 흡수됐는지, 기본 근무표가 오늘 포함 미래 계획만 보는지, `시간순` 삭제가 유지되는지, `기록`이 과거 실적 탭으로 분리됐는지, `직원별`이 시간 구간 색상 구분 보기로 정의됐는지 다시 확인한다.
- 제목 영역 높이, 보조 분석 데이터 면적, 근무표 행/열 노출량을 720p급 모니터와 폰 화면에서 함께 확인한다.
- 근무칸 터치 후 팝업 수정 흐름이 빠른 반복 수정의 기본인지, 핵심 수정이 2-3회 터치 안에 가능한지 확인한다.
- 코드 수정, 배포, live 사이트 반영은 별도 승인된 구현 작업에서만 한다.
